# 崧達企業管理系統 — 現況盤點與半年規劃（2026-11 ～ 2027-04）

> 2026-11-02 依程式碼實際盤點（頁面、API、排程、套件）整理。
> 承接 `operating-system-roadmap.md` 的長期方向與 `2026H2-計畫.md`；本文只管接下來六個月。
> 原則不變：**業務只回報客情，其餘都是系統的事**；自動化一律先影子模式，再建議，再自動執行。

## 一、現況盤點

## 二、半年規劃（按月，每月一個可驗收的閉環）

### 11 月：收尾上線的東西，把「系統會自己講話」補齊

| 項目 | 自動化設計 | 驗收 |
|---|---|---|
| 推播全裝置實測、接上「轄區新開業」「課程客戶到期」 | 夜間批次產生 → 直接通知該業務與主管，無需人點 | 每位業務手機收到過一則 |
| 報價轉訂貨單實測、修正 | — | 一張真實報價走完 |
| **排程健康監看** | 每支 cron 寫執行履歷到 Redis；連續失敗或超過 36 小時沒跑 → 推播給中央管理 | 故意停一支排程，隔天收到通知 |
| 技術規格補資料流程 | 後台一次貼整個系列的規格表（Excel 匯入，dry-run 預覽） | 前 10 個常報價系列有規格 |
| 報名防機器人（Turnstile） | 只在公開報名頁加，不影響登入系統 | 使用者取得金鑰後上線 |

### 12 月：年終數字自動長出來

| 項目 | 自動化設計 | 驗收 |
|---|---|---|
| 經營月報自動化 | 每月 1 日批次：覆蓋率、漏斗、名單成效、報價／訂單量 → 寫成月報頁，對比 7 月基線 | 老闆頁一鍵看 7 月 vs 12 月 |
| 月報推播 | 月初通知總經理、中央管理 | 12/1 自動送達 |
| 指標快照入庫 | 每月指標存 Redis／JSON（不進 Notion，避開 1 萬筆） | 可回看任何一個月 |
| 年終簡報資料包 | 一支 API 輸出三條故事線的真數字 | 簡報不用手算 |

### 1 月：個人工作佇列（業務只看一個清單）

現在首頁已有「接下來的工作」，但來源分散（追蹤、認領建議、拜訪建議、活動客戶、新開業、工單）。

| 項目 | 自動化設計 | 驗收 |
|---|---|---|
| 統一工作項模型 | 所有來源產生同一種「工作項」，有來源、建議動作、到期、自動結案條件 | 首頁只剩一個清單 |
| 自動結案全面化 | 回報客情、下訂單、工單關閉，都能自動收掉對應工作項 | 沒有任何「請點已處理」 |
| 主管例外視圖 | 只列「逾期未動」「無人認領」「高價值未接觸」 | 主管頁不需逐筆看 |
| 工作項分數第一版 | 規則式（客戶價值 × 久未拜訪 × 有商機訊號），可解釋 | 每項都能顯示「為什麼排前面」 |

### 2 月：技術支援閉環（工單 → 服務履約）

| 項目 | 自動化設計 | 驗收 |
|---|---|---|
| 工單狀態機與 SLA | 新建→指派→處理→結案；逾時自動升級通知主管 | 逾期工單主管必收到 |
| 設備保養預警 | 依設備安裝日與保養週期，到期前 30 天自動產生工作項給業務 | 第一批到期設備出現在佇列 |
| 客情→工單→設備串起來 | 維修工單自動掛到設備履歷，設備頁看到完整歷史 | 任一設備可看三年內工單 |
| 技服知識庫（審核式） | 結案工單的處理方式沉澱為條目，中央管理審核後上架 | 10 條以上可查 |

### 3 月：行政例外工作台

| 項目 | 自動化設計 | 驗收 |
|---|---|---|
| 訂單流程自動推進 | 已受理→出貨→完成由系統依狀態與時間推進；只有例外（缺貨、價格異常、促銷衝突）才進人工 | 行政每天只看例外清單 |
| 報名繳費核對 | 匯款後五碼＋金額自動對帳（需使用者決定是否接銀行對帳檔） | 未繳款名單自動產生 |
| 課程結案自動化 | 報到後自動更新客戶足跡、未到者進追蹤 | 課程結束當天足跡完成 |
| 自動化執行履歷 | 每個自動動作都留「誰、何時、為什麼、可回滾」 | 稽核頁可查 |

### 4 月：行銷歸因與資料底座決策

| 項目 | 自動化設計 | 驗收 |
|---|---|---|
| Campaign → 成交歸因 | 名單成員在期間內下單自動歸因，報表顯示每場戰役帶單 | 每場 Campaign 有成交數 |
| 課程續約／到期培育 | 到期前自動進業務佇列，到期後自動關 | 不漏一家 |
| 官網表單直通漏斗 | 官網留資料 → 自動建開發客戶、來源＝官網 | 測試名單進漏斗 |
| **Notion 搬遷決策** | 客情庫逼近 1 萬筆；提出「分庫（按年）」vs「搬到資料庫（Postgres）」的成本與風險，請使用者定案 | 有書面決策 |

## 三、整合候選（需使用者決定，標示成本）

| 整合 | 價值 | 成本／風險 |
|---|---|---|
| Cloudflare Turnstile | 報名防機器人 | 免費；需取得金鑰 |
| 公司網域短網址（如 `go.songtah.com.tw`） | 報名連結好看、可信 | 需設 DNS |
| 官網表單 → 客戶系統 | 名單自動進漏斗 | 官網需加一支呼叫 |
| 銀行對帳檔匯入 | 報名與訂單自動對帳 | 需銀行提供檔案格式；資料屬 L4 僅中央管理可看 |
| 會計／ERP 出貨資料 | 訂單完成自動判定、業績自動算 | 需確認公司現用系統能否匯出 |
| Google 日曆（出差規劃） | 拜訪行程同步到手機行事曆 | 需 OAuth；可先做 .ics 匯出 |
| LINE 官方帳號推播給客戶 | 課程、促銷通知 | 按則計費；對外發送需先問 |

## 四、自動化設計鐵則（每個新自動化都套）

1. **影子模式先跑兩週**：只記錄「系統會怎麼做」，不改資料、不發通知，和人工結果比對。
2. **建議模式**：產生工作項或通知，人可一鍵採納，系統記錄採納率。
3. **自動執行**：採納率穩定後才自動做，每次留履歷、可回滾。
4. **自己結案**：任何工作項與通知都要定義「什麼事發生就自動消失」；想不出來就不要做。
5. **不新增業務要填的欄位**；資料來源只能是客情回報、訂單、系統外部資料。
6. Notion 寫入一律 dry-run、印筆數與樣本、使用者核准；大量資料優先放 Redis／JSON。

## 五、風險與對策

| 風險 | 對策 |
|---|---|
| 採用率（業務不回報客情） | 1 月工作佇列讓回報有立即回饋；主管例外視圖讓漏報可見 |
| 客情庫 1 萬筆上限 | 12 月前先做分區掃描保護，4 月定案搬遷 |
| 單人維運 | 11 月排程監看 + `AGENTS.md` 交接；每月規劃可拆成獨立任務交給 Codex |
| Redis 免費額度 | 新增通知、履歷前估算指令數；超過先告知 |
| 自動化誤判（例如誤判歇業） | 一律保留一鍵復原；主管收到通知可即時糾正 |
