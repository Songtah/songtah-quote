## 2. 為什麼是「現場 QR」

1. 零成本、零新服務依賴。
2. 事後 Email 的觸及天花板只有 44.9%，且需新接寄信服務。
3. 現場當場填的回收率遠高於課後推送。
4. **業務全程零動作**，符合 CLAUDE.md 最高原則。
5. 每場 9–53 人，樣本小 → 回收率比題目數重要，題目必須短。

---

## 3. 完全匿名的設計後果（已與使用者確認並接受）

**放棄：**
- 回寫 `狀態=已到場`（出席資料缺口維持存在，需另循簽到解決）
- 個別業務線索（「某人對列印有興趣」無法產生）
- 精確回收率（無出席人數作分母）

**保留：**
- 每場的滿意度、講師評分、推薦度（NPS）統計 — token 綁活動，不綁人
- 「想深入的主題」的**場級彙總** → 下一季排課依據
- 低分預警 → 場級訊號（「這場有 N 份 ≤2 分」），非個人拜訪建議

**連帶技術限制：**
- 問卷回應**不得寫入報名 DB**（等同綁回個人），必須獨立 DB，只掛「活動」relation
- 不儲存 IP、不儲存精確時間（只存日期）；Notion 自動 `created_time` 視為可接受殘留風險
- 開放文字題須在 UI 明示「請勿填寫姓名或單位」——每場僅 9–53 人，自由文字極易反推身分

## 4. 架構（全部沿用既有模式，不發明新東西）

```
lib/survey-token.ts          ← 照抄 lib/checkin-token.ts（HMAC/NEXTAUTH_SECRET/fail-closed）
                                簽章字串改為 `survey:${eventId}`，與簽到 token 不互通
lib/notion/surveys.ts        ← 新葉領域（依 CLAUDE.md 葉領域不互依原則，自有 DB、不 import 其他葉領域）
app/survey/[eventId]/page.tsx        ← 公開頁，照抄 /checkin/[eventId] 的結構
app/api/public/survey/route.ts       ← withApiAuth 的明確例外，照抄 /api/public/checkin
components/EventDetailContent.tsx    ← 加「問卷 QR」與該場統計（QR 用既有 `qrcode` 套件，
                                        照抄該檔既有的 QRCode.toDataURL 寫法）
```

**開放窗**：活動開始日 ~ 結束日 + 7 天（比 `isCheckinOpen` 的 ±1 天放寬，
讓當場沒填的回家能補）。逾期顯示「本場問卷已截止」。

**觸發條件**：`活動類型 === '課程'` 自動具備問卷頁與 QR，**不新增任何勾選欄位**
（自動判定優於人工維護）。

## 5. 問卷題目（6 題，目標 90 秒）

不問姓名與單位。

| # | 題目 | 型態 | 必填 |
|---|---|---|---|
| 1 | 整體滿意度 | 1–5 單選 | ✓ |
| 2 | 講師講解清楚程度 | 1–5 單選 | ✓ |
| 3 | 實作時間 | 太少／剛好／太多 | ✓ |
| 4 | 會推薦同業參加嗎 | 1–5 單選 | ✓ |
| 5 | 最想再深入的主題 | 複選：掃描／設計／切削／列印／後處理／材料選用 | — |
| 6 | 其他建議 | 開放文字（標註勿填姓名單位） | — |

**第 5 題是整份問卷的商業價值所在**：把滿意度調查同時變成需求探測，
彙總結果直接產生下一季課表。選項刻意對齊官網的製程階段語彙，兩邊可互相印證。

第 4 題按 NPS 慣例計算：4–5 為推薦者、3 為中立、1–2 為貶損者。

## 6. Notion schema（新建 DB：課程問卷回應）

| 欄位 | 型態 | 備註 |
|---|---|---|
| 編號 | title | 隨機碼，**不得用流水號**（會洩漏填答順序） |
| 活動 | relation → 活動 DB | 唯一的關聯，無任何個人欄位 |
| 填答日 | date | 只到日 |
| 整體滿意度 | number | 1–5 |
| 講師清楚度 | number | 1–5 |
| 實作時間 | select | 太少／剛好／太多 |
| 推薦意願 | number | 1–5 |
| 想深入的主題 | multi-select | 六個製程階段 |
| 建議 | rich text | |

環境變數：`NOTION_SURVEYS_DB`，並比照 `lib/notion/shared.ts` 既有作法留 fallback id。

## 8. 反濫用（公開頁無登入，必備）

沿用 `/api/public/checkin` 的既有防線，另加一項：

1. HMAC token 驗證（fail-closed）
2. 開放窗檢查
3. IP 限流（**限流用，不落地儲存**）
4. honeypot 欄位
5. **每場回應數上限＝該場報名人數 × 1.5**，超過即拒收並在活動詳情頁示警
   （匿名無法逐人去重，改以場級上限擋灌票）
6. 前端 localStorage 軟性擋重複送出（可繞過，僅防誤觸）
